# Bảo mật E2E
HTTP là truyền tin bị MITM attack. HTTPs cản được vì thông tin truyền đi bị mã hóa khi thiết lập SSL connection với server. Nhưng như v server vẫn nhìn thấy nội dung data và biết thông tin nhạy cảm của user
Giao thức E2E giải quyết vấn đề: 2 users trao đổi pubkey qua server, mỗi user dùng pubkey của người kia để mã hoá trước khi gửi tới server, server chỉ forward tin tới đích. Private key được lưu local ở máy của user, quên pass sẽ kbh lấy lại tin nhắn được nữa.
=> Hacker tấn công server cũng k biết được message là gì, user phải nhớ mật khẩu mới xem được lịch sử tin nhắn.



# Bulk API Pattern
Tạo 1 endpoint /$batch cho user gửi 1 request chứa nhiều request khác. 

-> Odata batch dùng mutipart với từng phần là application/http => nên dùng thay vì JSON batch
Request:
POST /$batch
Content-Type: multipart/mixed; boundary=batch_123
Body:
--batch_123
Content-Type: text/plain

Hello

--batch_123
Content-Type: image/png

(binary data)

--batch_123
Content-Type: multipart/mixed; boundary=changeset_456

--changeset_456
Content-Type: application/http
Content-Transfer-Encoding: binary

POST /users HTTP/1.1
Content-Type: application/json
{
  "name": "Alice"
}
--changeset_456
Content-Type: application/http
Content-Transfer-Encoding: binary

DELETE /inventory/1 HTTP/1.1
--changeset_456--

--batch_123--

Server và client phải tự xử lý parse request và response thủ công.
changeset không chứa GET, chỉ chứa các action thay đổi data và server cần đảm bảo 1 changeset là 1 tx, 1 lệnh failed thì rollback cả changeset đó.
batch
  ├── GET
  ├── changeset A
      ├── POST
      ├── PATCH
      └── DELETE
  ├── GET
  └── changeset B
      ├── POST
      ├── PATCH
      └── DELETE
Kiểu Content-Type: multipart/mixed; boundary=abc123 thì multipart/mixed dùng nhiều kiểu dữ liệu, boundary là phần ngăn cách trong multipart. Còn có multipart/form-data chuyên dùng cho HTML form, VD <form enctype="multipart/form-data">
K có yêu cầu về chạy song song, có thể implement gom các hàm chung thành 1, chạy song song từng phần GET và changeset với nhau tuỳ.

# Fuzzy search alg
Thuật toán tìm kiếm gần đúng trên 1 list. Nhận vào 2 string và trả ra độ so khớp match nhau không.
Để search tự sửa lỗi chính ta, implement thêm spell corrector chấp nhận chuỗi đích có độ so khớp ở 1 mức thấp là được.
Ngoài ra còn có: Levenstein Distance Algorithm, N-gram Algorithm, BK Tree Algorithm, Bitap Algorithm

- Naive Algorithm: 
Duyệt 2 vòng for tìm input xuất hiện trong chuỗi đích trong list thì match. Tức chuỗi tìm kiếm phải liền nhau exactly đúng thứ tự.
- Hamming Distance Algorithm: 
Input là 2 chuỗi cùng kích thước, cho ra số lượng ký tự k khớp nhau. 
Thuật toán giúp tìm gần đúng chuỗi đích nhưng nhược điểm là chuỗi phải cùng độ dài, nếu k cùng độ dài sẽ k luôn k khớp nên kém linh hoạt trong trường hợp ký tự thêm bớt ký tự
- Levenshtein Distance (Edit Distance): 
Đo sự khác biệt giữa hai chuỗi bằng cách đếm số lượng các phép chèn, xóa, thay thế cần thiết để biến chuỗi này thành chuỗi kia.
Thuật toán tốt giúp sủa lỗi chính tả chuẩn

Nếu muốn tìm kiếm một chuỗi ngắn trong một danh sách các chuỗi rất dài sẽ phải duyệt qua từng chuỗi dài và so sánh chuỗi ngắn với các đoạn con của chuỗi dài. Việc này rất chậm và cần tiền xử lý nhiều thứ, khi gặp case này, ta thường dùng các công cụ như Elastic Search chứ k tự implement, Elastic Search có hỗ trợ fuzzy search.
MongoDB có index 'text' hỗ trợ fuzzy search kèm mức độ match
SQL có full text search hỗ trợ search fuzzy chuỗi ngắn trong chuỗi dài, có LIKE tìm đa dạng hơn nhưng chậm, chỉ dùng với tập data nhỏ
SQL có FREETEXT giúp tìm kiếm gần đúng từ đồng nghĩa như google 



# QPS 
Định luật 80/20 là 80% request trong 1 ngày rơi vào 20% thời gian. Nếu hệ thống có 2M request/ngày thì cần bnh QPS và nếu 1 server chịu được 60 QPS thì cần bnh server? 
QPS là số lượng query 1s. Response time là thời gian request đi và về. TPS là transaction per second. VD 1 TPS có 2 QPS tức 1 transaction query tới server 2 lần.
Server của ta cần xử lý được tải lúc giờ cao điểm mới được: 2M request * 80% = 1.6M request
86400 * 20% = 17280s tức 1.6M request rơi vào 20% thời gian là 17200s
QPS = 1.6M request / 17200s = 93 request/s => Cần 2 server hoạt động giờ cao điểm để chạy mượt mà.



# 2 kiểu crawling server
- Server liên tục check và crawl data tĩnh từ 1 nguồn, nếu có data mới thì update vào DB. VD mỗi 24h crawl 1 lần
Nhiều nền tảng họ tạo riêng 1 server để crawl hết các data vào container theo các rules xác định và cung ra API, rồi server sẽ query data trong phạm vi container đó, để tránh crawl data thừa => VD untrest k crawl data ngoài rules

- Server liên tục crawl data từ 1 nguồn, data đó liên tục thêm mới và có dấu thời gian, lượng data rất nhiều và không thể crawl hết 1 lúc. Ta có thể dừng lại và crawl tiếp từ vị trí trước bất cứ lúc nào. Khi crawl đến vị trí mới nhất, server tiếp tục chờ update realtime với data mới.
Đơn giản là lưu cả dấu thời gian vào db, cứ crawl là lấy dấu thời gian đó query tiếp cho tới hiện tại hoặc tới 1 mốc interval tiếp theo. Có cơ chế retry và atomic, đảm bảo dừng và crawl tiếp thoải mái. 
Nhiều nền tảng cho phép subscribe vào 1 nguồn data source là socket để lấy data mới. Phải implement catch error connection break thì tự reconnect và mail thông báo.



# Usecase horizontal scaling theo vị trí địa lý
Nginx có thể xử lý 1M connection đồng thời trên 1 single server. Vậy xử lý 100M request đồng thời thì sao? 
Dùng horizontal scaling mở rộng nhiều server và thêm load balancers. Scale với K8s, Docker. Dùng HTTP3, chống DDoS. Dùng cache, CDN, sharding, socket, message queue. Scale cả vertical. Bảo mật network, máy ảo. Track server load và capacity với monitoring tool. Autoscaling, backup server, thuật toán tự bầu cử tăng tính availability.

Thế nếu dùng load balancer, 100M request vào balancer đó thì toang? 
Dùng nhiều load balancer ở nhiều vị trí địa lý khác nhau. Nếu thực sự lớn thì chia tiếp layered load balancer theo vùng miền. Dùng CDN để giảm tải request tới server.

Có thể tạo 10 load balancer ở các châu lục khác nhau bằng 1 tk aws không? 
Có. Vào EC2 trong từng region tạo server, tạo Elastic Load Balancer trong EC2. Dùng Route 53 định tuyến người dùng từng khu vực vào các load balancer ở các vùng khác nhau. 

Làm sao để cấu hình cho user tự query server hoặc load balancer gần nhất? 
Dùng dịch vụ DNS; Dùng CDN; Ở các load balancer có thể cấu hình thêm các rules để forwards đến server nào khi có nhiều server; Dùng Anycast Routing cho phép 1 IP được gán cho nhiều server và hệ thống mạng tự động định tuyến đến server gần nhất.

Route 53 trong AWS sử dụng pp nào? 
Nó là pp routing dùng dịch vụ DNS Geolocation, có thể cấu hình để gửi cho server gần nhất, hay có độ trễ nhỏ nhất, hay trọng số ưu tiên được set lớn nhất, tuỳ. 

Nhưng nếu server phân tán mà database tập trung thì query vẫn lâu nếu db ở xa? 
Có thể replica database ở nhiều nơi, hoặc dùng db sharding chia ra ở nhiều khu vực như server luôn.
Replica update bị lâu nếu ở xa, nên dùng db sharding hơn. Khi đó data của các nước phải là độc lập nhau. Nó cũng giải quyết vấn đề về chính sách lưu trữ data ở các nước khác nhau có thể khác nhau. Cần thiết kế để query tới 1 nước phụ thuộc vào data chứ k phụ thuộc vào vị trí hiện tại của họ, VD 1 người di chuyển sang nước khác, họ vẫn query shard của nước gốc và chấp nhận query bị lâu hơn. Khi đó có thể tạo thêm cache cho case user di chuyển giữa các nước. 
Cách db sharding này lại k dùng khi cần đồng bộ data realtime các nước. VD tạo bảng xếp hạng toàn cầu.

Nếu replica thì data tự đồng bộ giữa các replica? 
Đúng là nó sẽ tự đồng bộ theo config, có nhiều loại replica khác nhau. 
- Sync replication ghi data đồng thời vào primary và secondary, nhất quán cao nhưng độ trễ cao
- Async replication ghi vào primary trước, secondary sau, sẽ có độ trễ và k nhất quán data
- Semi-sync rep: primary xác nhận 1 vài secondary xong là được
- Multi-master rep: ghi cùng lúc vào các master là coi như xong, k cần quan tâm secondary của các master xong hay chưa.
=> AWS hỗ trợ database có sẵn các tuỳ chọn sao chép data. VD dùng dynamoDB cho multi-master. Tuỳ vào mức độ realtime của data cần như nào.

Dùng replica nhưng 2 master ở 2 khu vực cùng được ghi vào đồng thời sẽ k nhất quán? 
Có thể xảy ra, nếu k cấu hình gì hết, 1 số db mặc định cho bản ghi cuối đè, 1 số db báo lỗi dữ liệu, tệ nhất là khi kết quả cuối cùng là 2 db chứa 2 data khác nhau. 
Nếu thực sự dùng update replica async mà bị xung đột như này, cần phải cấu hình xử lý thêm như versioning, last write wins, user custom rules, ưu tiên request đến từ source nào, lấy random, quorum-based systems, nếu 2 request kèm timestamp mà y hệt nhau thì chọn random chứ nhất quyết k xung đột.
VD trong sql có thể cấu hình SQL Server Merge Replication để xử lý conflict tự động theo rules của ta. Hoặc dùng cloud cung các dịch vụ tự động replica và tự đọng phát hiện xử lý xung đột sẵn mà k cần phải tự cấu hình thủ công.

Trong TH replica 1 master thì chỉ master có thể ghi, các slave chỉ đọc. Always On Availability Groups là 1 tính năng của SQL cho phép tự chuyển đổi dự phòng giữa các bản sao khi có sự cố, đảm bảo bất cứ thời điểm nào cũng luôn có 1 master.



# Backend for Frontend (BFF) Pattern
Là mô hình thiết kế dùng 1 server riêng tối ưu cho FE để dễ call API hơn 
Mỗi loại UI page nên có 1 BFF riêng. VD mobile có thể bỏ đi 1 vài dòng text hay ảnh thì response từ server có thể trim bớt để tối ưu.
Vd web có trang dashboard cần FE gọi 10 API 1 lúc và xử lý sẽ lag thì nên dựng 1 BFF server cung 1 API cho FE gọi, bên trong gọi 10 API (Promise.all) và trả ra kết quả đã xử lý cho FE. FE chỉ cần lo render lên UI.
VD: NextJS client ---Call BFF---> NextJS API ---Call---> 10 API services in BE server.
=> Thực tế nextjs dùng vậy cho tiện SSR, với case khác có thể viết API gom ở ngay server gốc được. Lưu ý chỉ tối ưu khi thực sự gặp vấn đề về performance



# Microservice là gì
Mô hình chia ra ứng dụng lớn thành nhiều module nhỏ, thay vì để nguyên khối. Các mô đun có thể được viết bằng nhiều ngôn ngữ khác nhau và tương tác thông qua API. Vì mỗi mô đun chỉ lo các tính năng riêng nhỏ nên code đơn giản.
Microservice cũng chỉ việc chia ra nhiều server nhỏ lo các chức năng riêng biệt hợp lại với nhau thành 1 hệ thống lớn.

Ngày xưa: Đặt hàng ---> Xử lý [100ms có hàng] ---> Mua hàng
Ngày nay: Đặt hàng --> Xử lý [100ms check giảm giá] [200ms tích điểm] [100ms hội viên] [...] --> Mua hàng
=> Thao tác đặt hàng có thể xử lý mất tới vài giây thay vì tức thì như trước. Do đó các hệ thống lớn tối ưu thông qua microservices, khiến nó trở thành:
Đặt hàng --> Xử lý [100ms] --> Mua hàng
            |  |     |    \ 
            v  v     v      v
      [100ms][200ms][100ms] [...]
Database, cache, messsagequeue là 3 loại storage lưu data buộc phải có trong các hệ thống lớn. VD ActiveMQ, RabbitMQ giúp triển khai mô hình MessageQueue cho microservices

#*** Hệ phân tán nhiều server thì query cái nào
Vấn đề muôn thuở của hệ phân tán khi dùng distributed cache, hoặc có nhiều api server và mỗi server dùng 1 cache riêng. Client query 1 server cache lưu có data rồi nhưng request sau query server khác không có phải get lại dẫn đến 1 data lưu ở nhiều server. 

Giải pháp là dùng pp Hashing hoặc Sticky Sessions thay cho Round Robin, Least Connections. 
Hashing sẽ hash thông tin client để lấy ra 1 server khiến cho mọi request của client luôn tới 1 server duy nhất. Nhưng dùng Hashing gặp vấn đề khi server list biến động, lúc nào client cũng gọi vào server đó kể cả khi nó sập hay bị xoá rồi dẫn đến lỗi. Do đó nên dùng:
- Consistent Hashing: 
Dùng 1 hàm hash an toàn cho id của node và id của data record. Ra 1 giá trị thì nhét vào 1 vòng tròn. Mỗi key sẽ gắn với node gần nhất kề nó theo chiều kim. Vd:
0 ---- A ---- key1 ---- B ---- key2 ---- E ---- key3 ---- C ---- key4 ---- D ---- 2^32-1
Key 1 gắn node B, key 2 gắn node E. Nếu ngừoi dùng muốn query data có key 4 thì họ query vào cache server D. Thêm xoá server không sợ lỗi mà lại nhanh.
- Rendezvous Hashing: 
Muốn tìm node nào lưu record hiện tại, ta tính weight của data với từng node: weight(key, node) = hash(key of record + node_id) => Node có giá trị cao nhất sẽ lưu record đó.
=> 2 pp này k những phân tán server mà còn phân tán data. Thực tế chỉ cần check nếu 1 server sập thì request vào fallback server tiếp theo cũng được.

-> Nhược điểm của dedicated server là k thể horizontal scaling, buộc phải mua thêm server ở nơi khác để horizontal scaling rất đắt.

-> Notification system: Giải quyết vấn đề 1 triệu shop gửi notification, 1 triệu user nhận được notification cùng lúc. Tốc độ cao và nhanh. Chắc chắn phải push notification tới user. Chỉ có MQ là đảm bảo tốc độ cao và không mất dữ liệu, không duplicate dữ liệu, đúng thứ tự.

Shop -> new product -> MessageQueue 1 -> User id từ 0 tới 1000
                    -> MessageQueue 2 -> User id từ 1000 tới 2000
=> Phân chia đảm bảo tốc độ push notification đạt tối đa khi có nhiều user

Phân tích:
Shop -> new product -> system.center.notification -> MQ -> 1,000,000 users

Về business: Notification center là database sẽ lưu tất cả notification của mọi shop. Trong 1 triệu user, user nào thường xuyên online, ta sẽ push notification tới cho họ. User nào online ít thì khi nào online, họ phải tự vào notification center mà pull về. Riêng trường hợp mã giảm giá hay tin quan trọng, sẽ phải push tới mọi user.

CrawlJob: Tại sao lại dùng 1 crawljob lấy data từ db của system.center.notification gửi tới MQ mà không gửi mẹ từ shop tới MQ luôn? 
Ta cần tính toán tới việc phân tác các case khi crash hệ thống. Trong trường hợp này cần đảm bảo khi 1 shop gửi notification tới user thành công, chắc chắn notification đó k bị mất khi crash hệ thống, nếu crash thì phải là chưa gửi chứ không phải là gửi thành công nhưng lại crash. Bởi vì việc gửi tới 1 triệu user phải làm từ từ, không thể chờ gửi hết 1 triệu mới báo thành công được. Do đó thành công ở đây là lưu thành công vào system.center.notification. Sau đó cần có 1 crawljob lấy từ db ra gửi vào MQ. 
Lại phải đảm bảo ở từng bước này, hệ thống crash tiếp nhưng khi khởi động lại vẫn chạy tiếp từ chỗ cũ. CrawlJob chỉ cần check trường isSent = false thì gửi tiếp thôi.

Việc phân phối trực tiếp từ system.center.notification tới database của user, so với gửi vào MQ và MQ gửi tới 1 triệu user có điểm lợi gì?
MQ cung khả năng đảm bảo tin nhắn không bị mất, mỗi thông báo chắc chắn sẽ được gửi đi ngay cả khi hệ thống lỗi. Ví dụ ta đang chạy for loop duyệt 1 triệu user để update db, chẳng may sập server phát sẽ mất. Để đảm bảo thì mỗi lần gửi user ta lại phải update database là đã gửi rồi, khởi động lại hệ thống sẽ check k gửi lại user đó nữa sẽ rất phức tạp nếu tự impleemnt. Nhưng MQ thì sập, khởi động lại sẽ tiếp tục từ chỗ dừng lại lần trước.
MQ cung khả năng xử lý tùy biến, ta có thể thêm workder để xử lý tin nhắn từ queue mà không cần thay đổi cơ sở hạ tầng của MQ. Kiểm soát số lượng tin nhắn worker xử lý song song, VD nếu CPU tốn quá thì giảm đi 1 chút để hoạt động trơn tru. Tách biệt quá trình tạo thông báo và gửi thông báo. Nếu server crash, MQ vẫn hoạt động bth, vẫn gửi tiếp các tin nhắn trong queue tới user.
MQ cung khả năng xử lý song song, nên nhớ chạy for loop sẽ xử lý tuần tự, k dùng MQ ta sẽ phải tự implement bất đồng bộ việc này khá mệt

Queue binding Topic subscription Dead letter queue Lock renewal Message scheduling Giải thích từng cái
Các khái niệm này thường xuất hiện trong hệ thống message queue/pub-sub như RabbitMQ, Apache Kafka, Azure Service Bus, Amazon SQS.
Mình giải thích theo kiểu dễ hình dung:

1. Queue Binding
Là gì?

Binding = “nối” queue với exchange/topic để message đi đúng nơi.

Ví dụ:

Producer gửi message vào Exchange
Exchange quyết định queue nào nhận message
Binding chính là luật kết nối đó
Ví dụ RabbitMQ
Producer
   ↓
Exchange
   ↓
Binding rule
   ↓
Queue

Binding có thể dựa trên:

routing key
pattern
wildcard

Ví dụ:

Queue A bind với routing key = order.created

=> Chỉ nhận message có key order.created

Dễ hiểu hơn

Giống:

Exchange = bưu điện
Queue = hộp thư
Binding = quy tắc phát thư
2. Topic Subscription
Là gì?

Subscription = đăng ký nhận message theo topic.

Consumer nói:

"Tôi muốn nhận mọi message về payment"
Ví dụ

Topics:

payment.created
payment.failed
order.created

Consumer subscribe:

payment.*

=> nhận:

payment.created
payment.failed
Khác Queue Binding thế nào?
Queue binding = cách queue được nối
Topic subscription = consumer đăng ký nhận topic

Nhiều hệ thống dùng 2 khái niệm gần giống nhau.

3. Dead Letter Queue (DLQ)
Là gì?

Queue đặc biệt chứa message bị lỗi không xử lý được.

Khi nào message vào DLQ?

Ví dụ:

Consumer crash nhiều lần
Retry quá số lần cho phép
Message invalid
Timeout
Flow
Main Queue
   ↓
Consumer fail
   ↓ retry fail
Dead Letter Queue
Tại sao cần?

Để:

không mất message
debug lỗi
xử lý lại sau
Ví dụ thực tế

Message:

{
  "userId": null
}

API xử lý luôn lỗi.

Sau 5 lần retry:

=> chuyển vào DLQ

Developer kiểm tra DLQ để fix.

4. Lock Renewal
Là gì?

Khi consumer lấy message, hệ thống “lock” message đó để consumer khác không xử lý trùng.

Nếu xử lý lâu:

lock có thể hết hạn
message bị consumer khác lấy lại

Lock renewal = gia hạn lock.

Ví dụ

Message cần xử lý 5 phút.

Nhưng lock chỉ 30 giây.

Consumer phải:

renew lock
renew lock
renew lock

để giữ quyền xử lý.

Nếu không renew?

Có thể:

message bị xử lý 2 lần
duplicate data
Hay gặp ở
Azure Service Bus
SQS visibility timeout extension
5. Message Scheduling
Là gì?

Gửi message nhưng chưa xử lý ngay.

Hệ thống sẽ delay đến thời điểm định trước.

Ví dụ
Gửi email sau 1 giờ

Producer:

schedule message at 10:00

Queue chỉ deliver lúc 10:00.

Use cases
Retry delayed
Fail → retry sau 5 phút
Reminder
Nhắc lịch ngày mai
Delayed job
Xử lý đơn hàng sau 30 phút
Tổng kết nhanh
Khái niệm	Ý nghĩa
Queue Binding	Nối queue với exchange/topic
Topic Subscription	Đăng ký nhận topic
Dead Letter Queue	Queue chứa message lỗi
Lock Renewal	Gia hạn quyền xử lý message
Message Scheduling	Hẹn giờ gửi/xử lý message

   ↓
Retry
   ↓
DLQ

   ↓
Lock renewal

   ↓
