# Bảo mật E2E
HTTP là truyền tin bị MITM attack
HTTPs cản được vì thông tin truyền đi bị mã hóa khi thiết lập SSL connection với server. Nhưng như v server vẫn nhìn thấy nội dung data và biết thông tin nhạy cảm của user

Giao thức E2E giải quyết vấn đề: 2 users trao đổi pubkey qua server, mỗi user dùng pubkey của người kia để mã hoá trước khi gửi tới server, server chỉ forward tin tới đích. Private key được lưu local ở máy của user, quên pass sẽ kbh lấy lại tin nhắn được nữa.
=> Hacker tấn công server cũng k biết được message là gì, user phải nhớ mật khẩu mới xem được lịch sử tin nhắn.

# Fuzzy search alg
Thuật toán tìm kiếm gần đúng trên 1 list. Nhận vào 2 string và trả ra độ so khớp match nhau không.
Để search tự sửa lỗi chính ta, implement thêm spell corrector chấp nhận chuỗi đích có độ so khớp ở 1 mức thấp là được.
Ngoài ra còn có: Levenstein Distance Algorithm, N-gram Algorithm, BK Tree Algorithm, Bitap Algorithm

-> Naive Algorithm: duyệt 2 vòng for tìm input xuất hiện trong chuỗi đích trong list thì match. Tức chuỗi tìm kiếm phải liền nhau exactly đúng thứ tự.

-> Hamming Distance Algorithm: input là 2 chuỗi cùng kích thước, cho ra số lượng ký tự k khớp nhau. 
Thuật toán giúp tìm gần đúng chuỗi đích nhưng nhược điểm là chuỗi phải cùng độ dài, nếu k cùng độ dài sẽ k luôn k khớp nên kém linh hoạt trong trường hợp ký tự thêm bớt ký tự

-> Levenshtein Distance (Edit Distance): đo sự khác biệt giữa hai chuỗi bằng cách đếm số lượng các phép chèn, xóa, thay thế cần thiết để biến chuỗi này thành chuỗi kia.
Thuật toán tốt giúp sủa lỗi chính tả chuẩn

=> Nếu muốn tìm kiếm một chuỗi ngắn trong một danh sách các chuỗi rất dài sẽ phải duyệt qua từng chuỗi dài và so sánh chuỗi ngắn với các đoạn con của chuỗi dài. Việc này rất chậm và cần tiền xử lý nhiều thứ, khi gặp case này, ta thường dùng các công cụ như Elastic Search chứ k tự implement, Elastic Search có hỗ trợ fuzzy search nhé. 



# QPS
-> Định luật 80/20 là 80% request trong 1 ngày rơi vào 20% thời gian. Nếu hệ thống có 2M request/ngày thì cần bnh QPS và nếu 1 server chịu được 60 QPS thì cần bnh server? 
QPS là số lượng query 1s. Response time là thời gian request đi và về. TPS là transaction per second. VD 1 TPS có 2 QPS tức 1 transaction query tới server 2 lần.
Server của ta cần xử lý được tải lúc giờ cao điểm mới được: 2M request * 80% = 1.6M request
86400 * 20% = 17280s tức 1.6M request rơi vào 20% thời gian là 17200s
QPS = 1.6M request / 17200s = 93 request/s => Cần 2 server hoạt động giờ cao điểm để chạy mượt mà.



# 2 kiểu crawling server
1) Server liên tục check và crawl data tĩnh từ 1 nguồn, nếu có data mới thì update vào DB. VD mỗi 24h crawl 1 lần
Nhiều nền tảng họ tạo riêng 1 server để crawl hết các container cần crawl về trước và cung ra API, rồi server sẽ query data trong phạm vi container đó, để tránh crawl data thừa => VD untrest
2) Server liên tục crawl data từ 1 nguồn, data đó liên tục thêm mới và có dấu thời gian, lượng data rất nhiều và không thể crawl hết 1 lúc. Ta có thể dừng lại và crawl tiếp từ vị trí trước bất cứ lúc nào. Khi crawl đến vị trí mới nhất, server tiếp tục chờ update realtime với data mới.
Đơn giản là lưu cả dấu thời gian vào db, cứ crawl là lấy dấu thời gian đó query tiếp cho tới hiện tại hoặc tới 1 mốc interval tiếp theo. Có cơ chế retry và atomic, đảm bảo dừng và crawl tiếp thoải mái. 
Nhiều nền tảng cho phép subscribe vào 1 nguồn data source là socket để lấy data mới. Phải implement catch error connect gãy thì tự reconnect và mail thông báo.



# Horizontal scaling theo vị trí địa lý
Nginx có thể xử lý 1M connection đồng thời trên 1 single server. Vậy xử lý 100M request đồng thời thì sao? Dùng horizontal scaling mở rộng nhiều server và thêm load balancers. Scale với K8s, Docker. Dùng HTTP3, chống DDoS. Dùng cache, CDN, sharding, socket, message queue. Nâng cấp chiều cao, bảo mật network, máy ảo. Track server load và capacity với monitoring tool. Autoscaling, backup server, thuật toán tự bầu cử tăng tính availability.

Thế nếu dùng load balancer, 100M request vào balancer đó thì toang? Dùng nhiều load balancer ở nhiều vị trí địa lý khác nhau. Nếu thực sự lớn thì dùng layered load balancer theo vùng miền. Dùng CDN để giảm tải request tới server.

Có thể tạo 10 load balancer ở các châu lục khác nhau bằng 1 tk aws không? Có. Vào EC2 trong từng region tạo server, tạo Elastic Load Balancer trong EC2. Dùng Route 53 định tuyến người dùng từng khu vực vào các load balancer ở các vùng khác nhau. 

Làm sao để cấu hình cho user tự query server hoặc load balancer gần nhất? Dùng dịch vụ DNS; Dùng CDN; Ở các load balancer có thể cấu hình thêm các rules để forwards đến server nào khi có nhiều server; Dùng Anycast Routing cho phép 1 IP được gán cho nhiều server và hệ thống mạng tự động định tuyến đến server gần nhất.

Route 53 trong AWS sử dụng pp nào? Nó là pp routing dùng dịch vụ DNS Geolocation, có thể cấu hình để gửi cho server gần nhất, hay có độ trễ nhỏ nhất, hay trọng số ưu tiên được set lớn nhất. 

Nhưng nếu server phân tán mà database tập trung thì query vẫn lâu nếu db ở xa? Có thể replica, hoặc data shard, hoặc cache lại, chia ra ở nhiều khu vực như server luôn.

Nếu replica thì data tự đồng bộ giữa các replica? Đúng, có nhiều loại replica khác nhau. 
- Sync replication ghi data đồng thời vào primary và secondary, nhất quán cao nhưng độ trễ cao
- Async replication ghi vào primary trước, secondary sau, sẽ có độ trễ và k nhất quán data
- Semi-sync rep: primary xác nhận 1 vài secondary xong là được
- Multi-master rep: ghi cùng lúc vào các master là coi như xong, k cần quan tâm secondary của các master xong hay chưa.
=> AWS hỗ trợ database có sẵn các tuỳ chọn sao chép data. VD dùng dynamoDB cho multi-master. Tuỳ vào mức độ realtime cần như nào.

Replica bị update lâu, tôi dùng shard chia theo location để tăng tốc? Khi đó data của các nước phải là độc lập nhau. Nó cũng giải quyết vấn đề về chính sách lưu trữ data ở các nước khác nhau có thể khác nhau. Cần thiết kế để query tới 1 nước phụ thuộc vào data chứ k phụ thuộc vào vị trí hiện tại của họ, VD 1 người di chuyển sang nước khác, họ vẫn query shard của nước gốc và chấp nhận query bị lâu hơn. 
Có thể tạo thêm cache cho case user di chuyển giữa các nước. 
=> K dùng khi cần đồng bộ data realtime các nước. VD tạo bảng xếp hạng toàn cầu.

Dùng replica nhưng 2 master ở 2 khu vực cùng được ghi vào đồng thời sẽ k nhất quán? Có thể xảy ra khi replica 2 chiều mà dùng async update. Nếu k cấu hình gì hết, 1 số db mặc định cho bản ghi cuối đè, 1 số db báo lỗi dữ liệu. Có thể xảy ra TH kết quả cuối cùng là 2 db chứa 2 data khác nhau. 
Thực tế ta chỉ cần dùng đúng loại replica cho từng case, khi nào update trong 1 tx, khi nào update async. Nếu thực sự dùng update replica async mà bị xung đột như này, cần phải cấu hình xử lý thêm như versioning, last write wins, user custom rules, ưu tiên request đến từ source nào, lấy random, quorum-based systems
VD trong sql có thể cấu hình SQL Server Merge Replication để xử lý conflict tự động theo rules của ta.

Dùng cloud cung các dịch vụ tự động replica và tự đọng phát hiện xử lý xung đột sẵn mà ta k cần phải tự cấu hình thủ công.

Trong TH replica 1 master thì chỉ master có thể ghi, các slave chỉ đọc. Always On Availability Groups là 1 tính năng của SQL cho phép tự chuyển đổi dự phòng giữa các bản sao khi có sự cố, đảm bảo bất cứ thời điểm nào cũng luôn có 1 master.
